## **Contexto Atual**

- O sistema já possui tabelas de heróis (`player_heroes`, `heroes_master`) com status base únicos por herói, elementos, subclasses, raridade, etc (gacha/summon).
- Heróis são obtidos via sistema gacha (summon), cada um com atributos exclusivos (atk, def, speed, skills, element, rarity, etc).
- Agora, foi implementado um sistema de CLASSES PRIMÁRIAS (Knight, Mage, Druid, Paladin/Ranger, Guardian etc) via tabela `classes`, com progressão de HP/Mana/Cap, e tabela `class_level_gains` para ganhos detalhados por level.
- Todo status de HP/Mana/Capacidade **deve ser calculado** pela classe+level, nunca salvo como fixo por herói.
- Todos atributos especiais e diferenciais dos heróis (atk, def, speed, rarity, element, skills, buffs, etc) continuam existindo e sendo utilizados normalmente. Eles são o "segredo" do diferencial do personagem, enquanto as classes são a base de progressão.

---

## **Princípios de Integração**

- **Classe Primária** → Progressão de HP/Mana/Cap (base e por level), balanceamento fácil e retroativo.
- **Herói Gacha** → Status base únicos (atk, def, speed, skills, rarity, element, buffs, etc); podem ser usados como modificadores, bônus ou para estratégias únicas.
- Ao consultar/mostrar um herói:  
  - Sempre calcule HP/Mana/Cap (classe+level)
  - Sempre mostre os atributos e diferenciais únicos do herói (atk, def, element, etc)

## **FASES DO ROADMAP**

### **Fase 0 — Levantamento e Diagnóstico**
1. Identificar todas as tabelas e campos de heróis, classes, atributos, skills, status, raridades, elementos, etc.
2. Mapear relações: player pode ter vários heróis, vínculo entre herói e classe, vínculo de skills, etc.
3. Documentar gaps: ausência de tabelas de classe/progressão, status fixos, etc.

### **Fase 1 — Banco de Dados**
1. Criar tabela `classes` com base e progressão de HP/Mana/Capacidade (**já feita**).
2. Criar tabela `class_level_gains` para ganhos detalhados por level/classe (**já feita/adaptada**).
3. Garantir tabelas de heróis (`heroes_master`, `player_heroes`) e status únicos estão preservadas.
4. **Atenção:** Não gravar HP/Mana/Capacidade fixos nos heróis; se houver, migrar para cálculo dinâmico.
5. **Checklist SQL:**  
   - Verifique existência e consistência das tabelas: `classes`, `class_level_gains`, `heroes_master`, `player_heroes`, `xp_table`, etc.

### **Fase 2 — Backend (Cálculo Dinâmico e API)**
1. Backend deve calcular HP/Mana/Capacidade em tempo real via classe+level (nunca buscar fixo do herói). **[CONCLUÍDO]**
2. Ao criar/sortear novo herói (gacha), vincular a classe primária correta. **[CONCLUÍDO]**
3. Ao consultar herói, retornar:  
   - HP/Mana/Cap calculados  
   - Todos outros atributos do herói (atk, def, skills, rarity, element, etc)  
   - Permitir buffs, modificadores temporários, mas nunca sobrescrever status base. **[CONCLUÍDO]**
4. Permitir balanceamento retroativo: mudar progressão de uma classe reflete em todos os heróis daquela classe. **[CONCLUÍDO]**
5. Garantir integração total com atributos herdados do sistema antigo (não perder valor estratégico de heróis únicos). **[CONCLUÍDO]**

### **Fase 3 — Frontend**
1. HUD dinâmica: mostrar barras e valores de HP/Mana/Capacidade calculados.
2. Perfil do herói: exibir classe primária, level, status calculados, atributos base do herói, raridade, skills, etc.
3. Feedback de progressão: notificar ganho de level, aumento de status, skills liberadas, buffs aplicados, raridade, etc.

### **Fase 4 — Testes, Balanceamento e Polimento**
1. Testar criação, consulta, level up, progressão retroativa e integração (heróis novos/gacha e antigos).
2. Validar integração de buffs, raridade, elementos, skills, etc.
3. Facilitar balanceamento: alterar classes/progressão deve refletir em todos os heróis automaticamente.
4. Documentar endpoints, lógica de cálculo, exemplos de consulta e resposta, estrutura das tabelas, exemplos de integração.
